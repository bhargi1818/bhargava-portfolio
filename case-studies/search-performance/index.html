MARBLE / 01 / PERFORMANCE

Fix the query. Keep the contract.

A search endpoint can be correct and still do far too much work. In Marble, substring matching became a focused database problem—not a reason to introduce another service.

RESULT / DESIGN OUTCOME263 → 0.05 ms

Synthetic no-match account query

TOOLS & CONCEPTS

PostgreSQL · Prisma · Query plans

CONTRIBUTION

Product and technical direction, agent-assisted implementation, review, and release decisions.

Devin contributed implementation. This case study describes the project work and its documented checks, not sole manual authorship.

The problem

Substring searches used case-insensitive, leading-wildcard matches. Ordinary B-tree indexes could not narrow those searches, so rare and missing terms required scanning the table. Pagination also needed a stable, explicit ordering.

The decision

The change added trigram GIN indexes on the fields the product actually searched, plus an ordering index for accounts. PostgreSQL still rechecked the original predicate. Unique tie-breakers made page boundaries deterministic; existing visibility rules remained in force.

What was checked

The implementation record includes real-Postgres integration checks for visibility, matching, pagination, index definitions, and query plans. On a local PostgreSQL 15.19 synthetic dataset with 330,000 users, the no-match account query fell from 263 ms to 0.05 ms (minimum of five warm runs).

The tradeoff

That number is a specific query benchmark, not end-to-end latency or a claim about production users. Common terms did not improve uniformly: one recipe query went from 36.5 ms to 50.1 ms as visibility joins dominated the cost. Later search work added typo tolerance; these figures describe the indexing change at that point in time.

Measure the expensive path, preserve product behavior, and report the cases that did not get faster.
