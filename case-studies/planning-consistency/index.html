MARBLE / 06 / PRODUCT CORRECTNESS

Make the preview, save, and screen agree.

A correct algorithm is only useful if its output survives the entire product journey. Marble’s meal-planning work exposed why shared data contracts matter.

RESULT / DESIGN OUTCOMEOne shared baseline

Across editor and calendar flows

TOOLS & CONCEPTS

State modeling · Transactions · Regression tests

CONTRIBUTION

Product and technical direction, agent-assisted implementation, review, and release decisions.

Devin contributed implementation. This case study describes the project work and its documented checks, not sole manual authorship.

The problem

The plan editor and calendar could enter the same optimization pipeline with different ingredient context. A separate issue allowed updated ingredient rows to coexist with an outdated or absent nutrition cache, so screens could disagree with the server.

The decision

The work introduced shared ingredient-baseline synthesis and rejected incomplete baselines. Materialized meals wrote their derived nutrition cache consistently. Apply responses carried persisted values, and undo snapshots included the state needed to restore the previous representation.

What was checked

The implementation history includes real-pipeline parity checks for calendar and editor entrypoints, coverage for meals without stored ingredient rows, tests for baseline completeness, and persistence/undo regression checks. Preview state remained tied to persisted state for concurrency checks.

The tradeoff

Switching a meal from proportional recipe arithmetic to ingredient-derived totals can change the displayed numbers. That is a product behavior change to explain and test. It is not evidence of clinical or dietary outcomes.

When two screens disagree, follow the state across every boundary before tuning the algorithm.
