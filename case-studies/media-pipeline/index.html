MARBLE / 05 / CLOUD SYSTEMS

Publish media once. Handle retries everywhere.

Media delivery is a consistency problem as much as a compression problem. Uploads, background jobs, database state, and cached URLs all have to agree.

RESULT / DESIGN OUTCOME3 HLS renditions

1080 / 720 / 480 size bounds

TOOLS & CONCEPTS

S3 · MediaConvert · EventBridge · CDN

CONTRIBUTION

Product and technical direction, agent-assisted implementation, review, and release decisions.

Devin contributed implementation. This case study describes the project work and its documented checks, not sole manual authorship.

The problem

Different media types followed different publication paths. Fixed output URLs could leave stale content in caches, and list screens lacked lightweight video posters. Duplicate events and interrupted transcodes could create conflicting results.

The decision

A unified server-owned pipeline produced versioned derivatives, image sizes, poster frames, adaptive video, and an MP4 fallback. Each transcode used isolated staging outputs. Publication checked ownership and the current source version before recording the result.

What was checked

The change record describes conditional object operations, job claims, row locking, terminal-event handling, and an idempotent backfill. It reports 4,389 unit tests and 82 real-Postgres integration tests passing across the backend at that revision.

The tradeoff

Those are suite-wide counts, not tests written solely for this feature. Keeping originals improves recovery and reprocessing but consumes storage. Database transactions and object-storage operations do not form one atomic transaction, so partial failures still need explicit recovery behavior.

Treat retries and partially completed work as normal operating conditions.

Evidence & scope

Engineering validation · unified media publication pipeline.
