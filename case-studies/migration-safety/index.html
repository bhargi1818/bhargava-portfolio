MARBLE / 03 / RELIABILITY

A green build should prove the upgrade path.

A test database that looks right is not enough. The release process must prove that the actual migration files can build that database.

RESULT / DESIGN OUTCOME115 migrations

Replayed onto an empty database

TOOLS & CONCEPTS

PostgreSQL · Prisma · GitHub Actions

CONTRIBUTION

Product and technical direction, agent-assisted implementation, review, and release decisions.

Devin contributed implementation. This case study describes the project work and its documented checks, not sole manual authorship.

The problem

CI created its test schema directly rather than executing migration history. Historical data-recovery migrations depended on rows that did not exist in an empty database. That left a gap between a passing test suite and a reproducible deployment path.

The decision

One shared database builder replayed the real migrations and compared the resulting schema with the declared model. The check was used by integration tests and deployment workflows, including paths triggered by direct pushes. One-off recovery operations were separated from replayable schema history.

What was checked

The implementation record reports 115 migrations applied successfully to a fresh database with no schema drift, followed by 12 integration suites and 116 passing tests. A deliberately broken migration caused the check to fail, demonstrating that the gate could actually stop a bad change.

The tradeoff

The count is a historical validation snapshot, not today’s migration count. Existing applied-migration behavior was checked separately; reproducibility on an empty database does not replace testing an upgrade against realistic existing data.

Test the path production takes—and deliberately exercise the failure path.
